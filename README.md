# SCM ReVamp (Swalpa Circular Maadi)

An industrial-symbiosis marketplace for Karnataka. Agents pool small waste lots, match sellers to buyers, negotiate price and freight, check KSPCB rules, and issue a hash-chained Digital Waste Passport for every approved deal.

This is the rebuild of the Bit N Build '26 hackathon project ([nanJR/SCM-Bit-N-Build-26](https://github.com/nanJR/SCM-Bit-N-Build-26)):

- **Backend:** Python (FastAPI and Pydantic), replacing the TypeScript engine.
- **Database:** Supabase (Postgres, PostGIS and row-level security), replacing Firebase.
- **LLM:** any free OpenAI-compatible provider. It is optional, and it only writes explanations.

## Layout

| Path | What it is |
| --- | --- |
| `backend/scm/` | The agents: `matchmaker`, `negotiation`, `logistics`, `regulator`, `ledger`, `paperwork`, and `pipeline` to run them in order. Also `api.py` (FastAPI) and `store.py` (in-memory or Supabase). |
| `frontend/` | The Vite + React app. Every API call goes through `src/lib/api.ts`. |
| `backend/tests/` | Parity tests against the old engine's output (`golden/legacy_pipeline.json`), plus ledger and API tests |
| `supabase/migrations/` | Schema, RLS policies, views and functions, in the order they were applied |
| `supabase/seed.sql` | Seed data generated by `scripts/gen_seed_sql.py`. Running it again is safe. |
| `docs/data-sources.md` | Where the real Karnataka data comes from (KSPCB Annual Report 2023-24, CSTEP, CPCB) |

## Run the backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest
uvicorn scm.api:app --reload
```

On Windows (Command Prompt or PowerShell), skip activation and call the venv's Python directly:

```bat
cd backend
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
.venv\Scripts\python.exe -m uvicorn scm.api:app --reload
```

By default the API uses an in-memory store and needs no keys. Open http://localhost:8000/docs to try the endpoints. The main ones are `POST /api/pipeline/run`, `GET /api/ledger` and `GET /api/decisions`.

## Run the frontend

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, with /api proxied to the backend on :8000
```

The tabs are Factories, Fleet, Match Deals, Negotiations, Passports, **KPIs** and **Audit**. KPIs shows SCOR-style network metrics for the latest run, such as perfect order rate, cost to serve, tonnes diverted, net CO₂ and the seller's share of surplus. Audit lists every agent decision from `decision_log`. Set `SCM_API_URL` if the backend is not running on `localhost:8000`.

### Sign-in and the My Desk tab

**My Desk** shows one workspace per role:

| Role | What the workspace shows |
| --- | --- |
| Seller | Your offers, private floor price, consent status and any disposal bill |
| Buyer | Supply offered to you, your quality specs and spend |
| Carrier | Trips quoted to you and freight earned |
| KSPCB regulator | Vetoes, disposal routing, refused sites and a consent watchlist |

Without Supabase settings, the tab runs in demo mode and you pick who to view as.

To turn on real accounts, run `cp .env.example .env.local` in `frontend/` and restart `npm run dev`. New users sign up as a seller, buyer or carrier. They then link their account to one unclaimed facility or fleet through `claim_facility` / `claim_carrier`, and each facility or fleet can only be claimed once. Regulator and admin roles can only be granted by an admin, in the `profiles` table.

Supabase asks new users to confirm their email by default. For local testing, you can turn that off in the Supabase dashboard under **Authentication → Sign In / Providers → Email**.

### Locking the API to signed-in users

By default the API trusts every caller as an admin, which is what the local demo needs. To make it check Supabase sign-in, start the backend with:

```powershell
$env:SCM_AUTH="required"
$env:SUPABASE_URL="https://oddtwtutmevpbgekqpzf.supabase.co"
$env:SUPABASE_PUBLISHABLE_KEY="sb_publishable_..."   # same key as frontend/.env.example
```

The frontend sends the signed-in user's access token, and `scm/auth.py` verifies it against the project's published signing keys. It then reads the user's role and linked facility or fleet from `profiles`, using the user's own token so row-level security still applies. `scm/scope.py` cuts each response down to that role:

| Caller | Deals, disposals and passports | Price floors and ceilings | Can do |
| --- | --- | --- | --- |
| Signed out | None | Hidden | Read the directory, verify the ledger |
| Seller or buyer | Only the ones their facility is party to, including pooled lots | Only their own | Report sensor readings for their own facility, register a new facility of their own kind, ask for a description |
| Carrier | Only trips they haul | Hidden | Ask for a description |
| Regulator | Everything | All | Run matching, read the audit log |
| Admin | Everything | All | Everything, including reset |

Ledger verification always checks the whole chain, even when only some passports are returned. If your project still signs tokens with the legacy HS256 secret, also set `SUPABASE_JWT_SECRET`. To make yourself an admin, change your row in `profiles` in the Supabase dashboard.

### Free LLM key

Groq is the easiest option. Sign up at https://console.groq.com with no card, create an API key, and then:

```bash
export SCM_LLM_PROVIDER=groq GROQ_API_KEY=gsk_...
```

The free tier is roughly 1,000 requests a day on `llama-3.3-70b-versatile`, which is plenty for this. If no key is set, every explanation falls back to a fixed template. Decisions stay exactly the same either way.

## Supabase

The migrations in `supabase/migrations/` are already applied to the project. To rebuild elsewhere, run them in order and then run `supabase/seed.sql`. Some design notes:

- Facility locations are PostGIS `geography` points. `facilities_within(id, km)` uses `ST_DWithin`.
- Reservation prices (cost floor and ceiling) are kept in `facility_private`, which only the owner or an admin can read. Other users can't see each other's walk-away price.
- `passports` is append-only, enforced by a trigger. `passport_chain()` lets anyone verify the public chain.
- Hazardous waste that no recycler takes is routed by the disposal agent (`scm/disposal.py`) to the cheapest operating KSPCB-listed TSDF, incinerator or cement co-processor. The generator pays the gate fee plus freight. The regulator refuses sites that are full or closed. For example, Harohalli TSDF has been full since 3 Feb 2021, so it is skipped and the waste goes to Dabaspet. The gate fees in that file are indicative placeholders, not quotes.
- Every agent decision is written to `decision_log` with its inputs, output, rule and reason.
- `reset_seed_facilities()` (behind `POST /api/reset`) puts the seed facilities back to their starting state. It leaves passports and decisions alone, so in Supabase mode a reset does not erase the ledger. In memory mode it starts over completely.

## Bugs fixed or found in the hackathon engine

The Python port reproduces the old engine's decisions exactly (see `tests/test_parity.py`), apart from these deliberate fixes:

1. **Passport hashes ignored the deal.** `JSON.stringify(obj, Object.keys(obj).sort())` uses the key array as an allowlist at every level, so nested fields were never hashed. Editing a price inside a passport went unnoticed. The ledger now hashes canonical JSON (`ledger.canonical_json`), and `tests/test_ledger.py` covers this.
2. **Consent dates in `dd/mm/yyyy` were not parsed.** These now parse correctly.
3. **Freight rates blew up on very short trips.** The buyer's freight budget was divided by the raw distance, so the 0.11 km F04 to F10 hop priced at INR 1,147 per tonne-km. Trips under 10 km are now billed as a 10 km minimum trip (`MIN_BILLABLE_KM`).

The following are still open, and are planned for Phase 2:

- Hazardous waste is priced as if the buyer pays the generator. In practice the generator pays a gate fee.
- The README described an alpha/beta concession curve that was never implemented.
- The old Firestore rules were `allow read, write: if true`.
